# 고스트 배틀의 플레이어 반응 지연 수정

1.8.4에 포함한 `1.8.3-feedback-r2` 후속 수정입니다. `feedback-r1`에서 플레이어 노트와 키 반응이 늦게 느껴진다는 보고를 조사했습니다. 아래 두 결함을 확인했으며, 실제 키 입력부터 화면·소리까지의 지연은 별도의 물리 장치 검증이 필요합니다.

## DXGI 프레임 대기열

기존 코드는 일반 스왑 체인에 `IDXGISwapChain2::SetMaximumFrameLatency(1)`을 호출했습니다. 이 API는 `FRAME_LATENCY_WAITABLE_OBJECT` 플래그가 있는 체인에만 유효합니다. 일반 체인에서는 호출이 실패하고, 바로 반환하여 장치 단위의 대체 제한도 적용되지 않았습니다. [Microsoft API 문서](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_3/nf-dxgi1_3-idxgiswapchain2-setmaximumframelatency).

이제 실제 체인의 플래그를 확인합니다. 일반 체인은 `IDXGIDevice1` 제한을 사용하고, waitable 체인의 개별 제한이 실패하거나 읽어 확인되지 않으면 장치 제한을 시도합니다. 초기화 시 `GetMaximumFrameLatency`로 값이 1인지 확인하고 로그에 남깁니다. 성공 여부가 확인되지 않으면 실패 로그를 남깁니다.

스왑 체인 생성 방식·전체화면·VSync·tearing 설정은 유지합니다. 새로운 waitable 체인으로 바꾸는 것보다 기존 표시 방식을 보존하면서 실패한 제한을 복구하는 편이 수정 범위와 회귀 위험을 줄입니다. 이 수정은 솔로 플레이에도 적용됩니다. 대기열 제한이 1이라는 것은 입력부터 디스플레이까지 정확히 한 프레임 걸린다는 뜻은 아닙니다.

## 긴 LN과 HUD 검색

HUD는 오디오·입력 처리와 같은 엔진 잠금 안에서 플레이어와 고스트의 상태를 읽습니다. 기존 검색 시작점은 첫 LN의 꼬리가 화면 범위를 벗어나야 전진했습니다. 긴 LN 하나가 남으면 그 사이의 지난 노트를 매번 다시 확인했고, 고스트 배틀에서는 같은 작업을 두 번 수행했습니다. 아직 숨겨지지 않은 지난 노트가 HUD의 최대 128칸을 채워 앞으로 나올 노트를 누락시키는 경우도 있었습니다.

검색 시작점을 노트 머리 시각으로 전진시키고, 꼬리가 남아 있는 이전 LN의 인덱스만 별도로 보관합니다. 매번 전체 이력을 읽는 대신 현재 표시 범위와 남아 있는 LN만 확인합니다. 누르고 있는 LN은 기존처럼 우선 표시하며, 놓친 LN의 남은 몸통도 유지합니다. 일시정지 재개 등으로 재생 시각이 되돌아가거나 비주얼 오프셋 때문에 과거 표시 범위가 넓어지면 검색 상태를 복구합니다.

엔진 잠금을 없애거나 고스트를 다른 스레드로 옮기지 않습니다. 노트 숨김 상태·누르고 있는 LN·판정 정보가 같은 엔진 시점에서 나온다는 조건을 유지하면서 중복 검색을 줄입니다. 플레이어 필드 크기, 스크롤 비율, 판정 시각과 리플레이 규칙은 유지합니다.

## 검증 도구와 해석

- 회귀 테스트는 긴 LN과 많은 과거 노트가 함께 있을 때 미래 노트와 LN 꼬리가 보존되는지, 시각이 되돌아가거나 표시 범위가 커져도 노트가 복구되는지 확인합니다.
- `TENRIFF_BENCH_GHOST_HUD=1`로 단위 테스트를 실행하면 합성 대형 차트의 HUD 생성과 오디오 콜백 시간을 출력합니다. 연속 HUD 읽기 경합은 실제 8ms 갱신 간격과 다른 스트레스 조건이며 실제 게임 지연으로 해석하면 안 됩니다.
- `menu_visual_preview --ghost --keys 8 --note-width 0.6 --1080p --no-vsync --fixture-time 1.25 --benchmark-frames 300 --benchmark-json benchmark.json`으로 실제 D3D 렌더 호출을 측정할 수 있습니다. 솔로 비교는 `--ghost`를 `--gameplay`로 바꿉니다. 벤치마크에서만 기존 프리뷰 프레임 대기를 없애고, 준비 프레임 이후 호출 시간과 Present 시간을 분리해 저장합니다.
- 창이 보이는 상태에서 실행해야 합니다. 숨김·가림으로 정상 Present 수가 요청한 프레임 수보다 적으면 도구는 실패로 종료합니다. `--exclusive-fullscreen`은 개발용 실제 전체화면 표시 확인이며, 보고서의 `fullscreen_presents`로 실제 적용 여부를 구분합니다.
- `pre_present_ms`에는 `EndDraw`에서 GPU를 기다린 시간이 포함될 수 있습니다. 순수 CPU 시간은 별도 프로세스 CPU 지표로 확인하며, 어느 지표도 물리 키보드·오디오 장치의 종단 간 지연을 측정하지 않습니다. 평소 게임에서는 이 벤치마크 계측이 꺼져 있습니다.

## 1.8.4 자동 화면 표시 확인

동일한 검사 실행본을 제한된 실행 환경과 실제 Windows 데스크톱에서 비교했습니다. 제한된 환경에서는 정상 Present가 0이었지만 실제 데스크톱에서는 창 모드·독점 전체화면 각각 VSync ON/OFF 네 조합 모두 정상 Present 30/30을 확인했습니다. 독점 전체화면은 실제 전체화면 Present도 30/30이며 검사 후 데스크톱 모드를 복원했습니다. 이전 실패를 우회해 성공으로 계산하거나 검사 조건을 낮추지 않았습니다. 최종 릴리스의 검증 범위는 [1.8.4 릴리스 검증](release-1.8.4-gate.md)에 정리합니다.
