# 1.8.8 결과 분석 기준과 플러그인·1.9.0 계획

2026-10-12 확정 범위는 **1.8.8 결과 분석 구현과 향후 계획 문서화**입니다. 이 소스는 미배포 로컬 개발 후보입니다. 이 문서는 분석 데이터의 의미와 검증 조건을 정리하며, 로컬 테스트 결과를 정식 출시나 실기기 타이밍 검증으로 대신하지 않습니다. 플러그인 실행 환경·API·SDK와 1.9.0 안정화는 계획이며 이번 구현에 포함되지 않습니다.

현재 고정 기준은 [TenRiff 1.8.7](baseline-1.8.7.md), 태그 `1.8.7`, 커밋 `6b060ad47b950ad9e0dbc516fbb40189e8e21347`입니다. 1.8.8 개발이 고정 기준을 자동으로 바꾸지 않으며 기존 태그와 배포 파일을 수정하지 않습니다. 로컬 구현 검증과 정식 릴리스 검증은 별도로 다룹니다.

후속 범위에 자유 해상도·결과 스크린샷 안내·여러 박 길이의 LN Mix가 추가되었습니다. 각 기능과 최종 검증 상태는 [1.8.8 추가 릴리스 조건](release-conditions-1.8.8.ko.md)에 기록합니다. 아래 분석 정의와 플러그인 계획은 유지하며, 초기 분석 후보의 검증 수치로 추가 기능까지 검증했다고 주장하지 않습니다.

## 분석으로 답할 질문

| 항목 | 보여 줄 정보 | 해석할 때의 기준 |
| --- | --- | --- |
| 레인별 타이밍 | FAST/SLOW 분포와 측정 표본 수 | 실제 플레이 레인 기준이며 빈 레인을 정확한 레인으로 표시하지 않음 |
| 곡 시간대별 정확도 | 시간 구간별 정확도와 판정 표본 수 | 타이밍 평균과 정확도는 구분하고, 구간 경계와 분모를 명시 |
| 단노트와 LN | 단노트, LN 시작, 의미 있는 LN 해제의 별도 타이밍 | 서로 다른 사건을 한 평균으로만 합치지 않음 |
| LN 유지 실패 | 유지 실패 횟수와 측정 불가능한 항목 | 실패를 정확한 `0 ms` 입력으로 만들지 않음 |
| 흔들림과 편향 | 부호 있는 평균, 분포, 표본 수와 흩어짐 | 평균이 0이어도 타건이 정확했다고 단정하지 않음 |

예를 들어 측정값이 `−20 ms, +20 ms`라면 부호 있는 평균은 `0 ms`지만 두 표본이 각각 빠르고 늦었다는 분포를 보존해야 합니다. `n=0`은 측정 자료가 없다는 뜻이며 평균 `0 ms`나 정확도 `100%`를 대신 표시해서는 안 됩니다.

## 로컬 분석 구현의 데이터 의미

분석 집계는 [`TimingAnalysis.h`](../src/gameplay/TimingAnalysis.h)와 [`TimingAnalysis.cpp`](../src/gameplay/TimingAnalysis.cpp)에 정의합니다. 본체 내부의 관찰용 자료이며, 아직 고정된 플러그인 API가 아닙니다. 입력·오디오 경로에서 사건마다 고정 크기 배열의 집계만 갱신하고 분포 표본을 가변 길이로 쌓거나 외부 코드를 호출하지 않습니다.

| 값 | 정의 |
| --- | --- |
| 측정 표본 `N` | 유한한 타이밍 오차가 실제로 측정된 사건 수 |
| 부호 있는 평균 | 측정 오차의 평균. 음수는 빠름, 양수는 늦음 |
| 평균 절대 오차 | 측정 오차의 절댓값 평균. 빠름과 늦음이 상쇄되지 않음 |
| 표준편차 | 측정 표본의 표준편차, 분모 `N−1`. `N<2`이면 화면에 `--` 표시 |
| FAST / SLOW | 기존 표시 계약대로 PG를 제외하고 각각 `<−0.05 ms` / `>+0.05 ms`인 측정 사건 수 |
| EARLY / LATE / CENTER | PG를 포함한 전체 측정 표본의 방향. CENTER는 `−0.05 ms`부터 `+0.05 ms`까지 |
| 타이밍 분포 | 42칸: `<−100 ms`, `[-100,100) ms`의 5ms 간격 40칸, `≥100 ms`. 가운데 40칸은 왼쪽 경계를 포함하고 오른쪽 경계를 제외 |
| 측정 불가 미스 | 대응 입력이 없는 놓친 단노트·LN 시작 또는 해제 제한시간 초과. 측정 표본/분포에는 포함하지 않음 |

FAST/SLOW 합계와 `N`은 일치하지 않을 수 있습니다. PG와 중앙 범위도 분포에는 남으며, 별도의 EARLY/LATE 집계가 그 편향을 설명합니다. 자동 LN 완료와 빈 타건 POOR는 판정 사건 수에는 포함되지만 타이밍 표본이나 측정 불가 미스로 세지 않습니다. 대상 노트가 없는 빈 타건에서 존재하지 않는 기준 시각을 만들어내지 않기 때문입니다.

곡 시간대는 전체 분석 길이를 **동일한 길이의 12구간**으로 나눕니다. 단노트/LN 시작은 채보의 시작 위치, LN 꼬리는 채보의 끝 위치, 빈 타건은 실제 입력 위치에 배치합니다. 따라서 늦게 확정된 판정도 원래의 채보 구간에서 볼 수 있습니다. 경계 밖 위치는 첫/마지막 구간에 모읍니다.

시간대 정확도는 기존 일반 판정 정확도와 같은 `PG=1.0, GR=0.8, GD=0.5, BD=0.2, PR=0`의 가중 평균입니다. 정확도 분모는 판정 가중치 합계이며, 성공적으로 시작한 LN의 머리·꼬리는 각각 기존 `0.5` 가중치를 사용합니다. 판정 사건 수와 가중치 분모를 구분하고, 측정 불가 미스가 있어도 타이밍 통계만 제외할 뿐 판정 정확도에서 지우지 않습니다. 상세 정확도나 새로운 점수 체계가 아닙니다.

레인 집계는 변환을 적용한 실제 플레이 레인 기준입니다. 내부 분석 자료는 기존 리플레이의 최대 32레인 범위를 보존하고, 현재 메뉴의 키 모드 선택 범위는 16레인까지 유지합니다.

## 결과 화면 사용

단독 결과 화면 위쪽의 **요약 / 레인 / 노트 종류 / 시간대** 탭을 클릭하거나 `F2`로 순환합니다. 분석 탭에서 `Esc` 또는 `Backspace`를 누르면 요약으로 돌아갑니다. `Enter`로 계속 진행하며 기존 `R` 재도전, `F1` 리플레이 기능도 유지합니다. 재도전과 리플레이에는 기존 채보·리플레이가 필요합니다.

결과 요약·분석 탭·멀티 결과 하단의 작은 `F9` 안내로 현재 화면을 PNG로 저장할 수 있습니다. 저장 위치와 추가 검증 범위는 [스크린샷 안내](release-conditions-1.8.8.ko.md#결과-스크린샷-안내)를 참고하세요.

- **레인:** 각 레인의 실측 분포, 측정 `N`, FAST/SLOW, 측정 불가 미스, 평균·평균 절대 오차·표준편차를 비교합니다. 각 분포의 세로 높이는 해당 분포의 최댓값 기준이므로 높이만으로 서로의 표본 수를 비교하지 말고 `N`을 함께 봅니다. 16레인을 넘는 리플레이 자료는 위/아래 키 또는 레인 범위 버튼으로 1~16 / 17~32 묶음을 전환합니다.
- **노트 종류:** 실제 사건이 있는 종류만 표시합니다. 단노트·LN 시작·LN 해제·LN 유지 실패·자동 완료·빈 타건을 구분하며 자동 완료를 `0 ms` 타건으로 표시하지 않습니다.
- **시간대:** 12개 채보 시간 구간마다 기존 판정 정확도와 판정 사건 수 `N`을 보여 줍니다. 이 화면의 `N`은 실측 타이밍 표본 수가 아닙니다. 아직 플레이하지 않았거나 판정이 없는 구간은 `0%` 대신 `--`입니다.

예전 기록에 분석 자료가 없으면 해당 상태를 안내합니다. 리플레이를 실제로 재생해 새 분석을 계산할 수 있지만 이전 평균을 복제해 분포를 만들지는 않습니다. 멀티플레이 결과는 기존 순위 화면을 유지하며 상대방의 상세 입력이나 분포를 추정하지 않습니다.

## 선택적 분석 저장 형식

결과·리플레이 JSON에는 사용 가능한 분석만 `stats.analysis_v1` 객체로 추가합니다. 이는 공식 점수/리플레이/판정 규칙 버전과 분리된 관찰용 메타데이터이며 리플레이 검증의 근거로 사용하지 않습니다. 자료가 없거나 유효하지 않으면 객체를 내보내지 않습니다. 직렬화·읽기 경계는 [`TimingAnalysisJson.h`](../src/gameplay/TimingAnalysisJson.h)에 정의합니다.

| 영역 | 내용 |
| --- | --- |
| 형식 | `version: 1`, `lane_count`, `sample_rate`, `duration_samples` |
| 분포 경계 | `histogram_min_ms: -100`, `histogram_bin_width_ms: 5`, 분포당 42칸 |
| 전체·레인 | `total` 분포와 `lane_count`개 원소의 `by_lane` 배열 |
| 사건 종류 | `by_kind`: `tap`, `ln_head`, `ln_release`, `hold_failure`, `auto_completion`, `empty_poor` |
| 분포 값 | 사건·실측·측정 불가 미스 수, EARLY/LATE/CENTER, FAST/SLOW, 평균·평균 절대 오차·중심제곱합 `m2_delta_ms`, `histogram` |
| 시간 구간 | 12개 `segments`: 각 `event_count`, `accuracy_points`, `accuracy_weight` |

분석이 없거나 버전을 지원하지 않거나 구조·유한 수치·집계 합계가 유효하지 않으면 분석 전체를 사용 불가로 처리하고 기존 기록은 계속 읽습니다. 예전 총 평균값을 표본 목록으로 확장하지 않습니다. 새로운 결과·리플레이 JSON 수치 출력은 왕복 가능한 정밀도를 사용해 집계 수치와 타이밍 모멘트가 불필요하게 반올림되지 않게 합니다.

이 형식은 현재 분석 보존을 위한 선택적 버전입니다. 플러그인의 안정된 공개 API 또는 플러그인 실행 지원을 뜻하지 않습니다.

## 판정과 측정의 경계

분석은 본체가 확정한 판정 결과를 설명합니다. 분석을 추가하려고 입력 보정, 오디오 시계, 판정창, 점수, 콤보, 게이지, 리플레이 재현 규칙을 바꾸지 않습니다. 적용 규칙은 [판정창과 LN 규칙](judgement-windows.md)을 따릅니다.

- **단노트 타건:** 대상 노트와 연결된 실제 타건이 있을 때만 타이밍 표본을 만듭니다.
- **LN 시작 타건:** LN 머리를 친 시점의 오차를 단노트와 구분합니다.
- **LN 해제:** 현재 규칙이 실제 해제 타이밍을 판정하는 경우에만 그 의미로 표시합니다. `#LNMODE 2` CN과 일반 LN에서 실제 해제 판정을 받은 입력을 포함하며, 일반 LN의 끝까지 누르기 자동 성공과 구분합니다. 해제 입력 없이 제한시간을 넘긴 꼬리는 LN 해제 항목의 측정 불가 미스입니다.
- **LN 유지 실패:** 실제 해제가 BAD로 확정된 사건을 별도로 셉니다. 타이밍을 측정한 실패는 해당 해제 오차를 유지 실패 분포에 보존합니다. 실패를 되돌리거나 추가 점수 벌점을 만들지 않고, 실제 판정이 확정한 실패만 설명합니다. 해제 입력 자체가 없는 제한시간 초과와 구분합니다.
- **자동 완료:** 일반 LN을 끝까지 누른 뒤 자동으로 완료한 꼬리는 실제로 `0 ms`에 뗀 표본이 아닙니다. 정확도에서 사용하는 기존 판정의 의미는 유지하되 해제 타이밍 분포에는 가짜 표본을 넣지 않습니다.
- **측정 불가 미스:** 대응되는 타건/해제가 없는 미스는 측정 불가로 셉니다. 평균·분산·FAST/SLOW 분포의 분모에 `0 ms`로 추가하지 않습니다. 판정 정확도에서는 기존 규칙에 따른 미스의 영향을 유지합니다.
- **추가 자료가 없는 기록:** 이전 기록에 분석 자료가 없으면 자료 없음으로 표시합니다. 기존 평균이나 총 미스 수로 레인·노트 종류·해제 표본을 추정해서 채우지 않습니다.

표본 수는 타이밍을 측정한 사건 수입니다. LN의 판정 가중치와 타이밍 표본 수는 다른 개념이므로, 표시하거나 저장할 때 서로 대신 사용하지 않습니다. 자동 연주 등 사람의 실제 타건이 아닌 결과를 사람의 타이밍 실력으로 오해하게 설명하지 않습니다.

## 1.8.8 검증 기준

초기 분석 후보에서 실제로 수행한 검사와 한계는 [초기 로컬 검증 기록](local-analysis-validation.ko.md)에 보존합니다. 후속 기능을 포함한 새 후보는 [추가 릴리스 조건](release-conditions-1.8.8.ko.md)의 별도 검증을 통과해야 합니다.

이 목록은 완료 판정 기준이며, 항목의 존재만으로 통과를 주장하지 않습니다.

- `−20 ms / +20 ms` 교대 입력은 평균 0과 0이 아닌 흩어짐을 함께 보존합니다. FAST와 SLOW 분포 및 표본 수가 일치해야 합니다.
- 놓친 단노트, 놓친 LN 시작, 해제 입력이 없는 꼬리 실패를 각각 확인하고 측정 불가 사건이 타이밍 평균에 포함되지 않아야 합니다.
- 일반 LN 자동 완료, CN 실제 해제, 너무 이른 해제에 따른 유지 실패가 구분되어야 합니다. 적용 규칙에서 의미 없는 해제 항목은 표본이 있는 것처럼 표시하지 않아야 합니다.
- 레인별·노트 종류별·시간대별 집계가 동일한 사건 집합과 일치해야 합니다. 빈 구간과 작은 표본도 표본 수를 표시해야 합니다.
- 같은 채보와 입력으로 기존 판정·점수·콤보·게이지·리플레이 결과가 유지되어야 합니다. 과거 규칙으로 재생하는 기록도 해당 규칙의 의미를 지켜야 합니다.
- 기존 기록을 열 수 있어야 하며, 새 분석 자료가 없는 기록을 분석 가능한 기록으로 오인시키지 않아야 합니다.
- 실제 결과 화면에서 키보드·마우스 조작, 읽을 수 있는 분포/표본 수, 정보가 없는 상태를 확인해야 합니다. 분석 수집이 입력·오디오 처리에 무제한 작업이나 외부 코드 호출을 추가하지 않아야 합니다.

물리 입력·오디오 지연, 다른 PC, 장시간 플레이의 증거는 단위 테스트나 화면 캡처와 구분해 기록합니다.

## 플러그인 시험판 계획 — 아직 구현하지 않음

목표는 사용자가 AI와 함께 **공개 API와 샘플로 개인 모드**를 만드는 것입니다. 매번 텐리프 전체 소스를 수정해야 한다면 안정판을 유지하는 목적을 충족하지 못합니다.

| 본체가 소유할 것 | 첫 플러그인에 허용할 것 |
| --- | --- |
| 입력 처리, 오디오 시계, 판정, 점수 계산 | 본체가 제공하는 읽기 전용 분석·표시 데이터 |
| 공식 기록 저장·검증 | 공식 기록과 분리된 분석 결과와 개인 설정 저장 |
| 멀티플레이 규칙과 세션 상태 | 허용된 결과 화면, 선곡 정렬·필터, HUD 영역과 메뉴 확장 |

분석 데이터에 이름과 의미를 붙이는 1.8.8 작업은 준비 단계입니다. 내부 구조를 그대로 안정된 공개 API로 선언하거나 이번에 실행 가능한 플러그인 형식이 생겼다고 설명하지 않습니다.

### 응답성을 보호하는 실행 경계

외부 플러그인은 본체와 분리된 실행 환경에서 처리합니다. 본체는 플러그인 계산이 끝나기를 기다리지 않으며 입력·오디오 처리 경로에서 외부 코드를 직접 호출하지 않습니다. 플러그인이 늦거나 실패해도 기본 화면과 플레이가 계속 동작해야 합니다. 별도 확장 호스트라는 방향은 [VS Code Extension Host](https://code.visualstudio.com/api/advanced-topics/extension-host)를 참고한 설계 목표이며, 텐리프에서 검증이 끝난 구조라는 의미는 아닙니다.

접근 권한과 실행시간은 별도로 제한합니다. 허용된 데이터·저장 영역만 접근하게 하는 경계와 무한 루프·CPU 과소비를 멈추는 경계가 모두 필요합니다. 출력 크기·빈도와 메모리도 상한을 두고, 예산 초과 시 확장을 중단한 뒤 기본 표시로 복구합니다. 외부 접근 인터페이스를 제한하는 [Wasmtime 보안 모델](https://docs.wasmtime.dev/security.html)과 실행량/시간 기준의 [실행 중단 기능](https://docs.wasmtime.dev/examples-interrupting-wasm.html)을 참고합니다. WebAssembly, Wasmtime 또는 특정 언어의 채택은 확정하지 않았습니다.

시험판에서 응답 없는 플러그인, 예산 초과, 잘못된 결과, 권한 없는 접근을 실제로 주입해 격리·중단·복구를 확인하고 구체적인 예산을 정합니다. 단순히 예외를 잡을 수 있다는 사실만으로 실행 경계를 통과한 것으로 보지 않습니다.

### 멀티플레이에서의 기본 동작

멀티 세션에서는 **본체가 외부 플러그인 실행과 결과 적용을 차단**합니다. 플러그인에게 스스로 꺼 달라고 요청하는 방식에 의존하지 않습니다. 이미 플러그인이 영향을 준 플레이 상태도 기본 규칙으로 다시 구성하고, 지연 도착한 외부 결과가 멀티 상태에 적용되지 않게 합니다.

복구 대상은 플러그인의 영향입니다. 사용자의 키 배치와 오디오 오프셋 같은 개인 입력 환경은 초기화하지 않습니다. 멀티 진입·이탈과 재접속에서도 이 경계가 유지되는지 시험판에서 확인합니다.

첫 API는 판정·채보·입력을 바꾸는 기능을 열지 않습니다. 향후 싱글 플레이에서 이를 허용한다면 해당 기록을 기본 기록과 분리하는 정책과 검증을 먼저 마련합니다. 멀티에서 비활성화한다는 조건만으로 싱글 기록 비교 가능성이 보장되지는 않습니다.

### API를 고정하기 전에 만들 샘플과 SDK

1. 같은 읽기 전용 분석 자료로 다른 구성의 결과 분석 화면을 만듭니다.
2. 허용된 곡 메타데이터로 개인 선곡 필터를 만듭니다.
3. 두 샘플 모두 본체 코드 수정 없이 설치·실행·비활성화할 수 있어야 합니다. 매번 엔진 내부 수정이 필요하면 API 고정을 미룹니다.
4. API 문서, 바로 실행되는 두 샘플, 오류 원인을 확인할 로그, 플러그인 없이 시작하는 안전 모드를 작은 개발 키트로 제공합니다.
5. 잘못된 API 버전, 고장 난 플러그인, 설정 저장 실패, 멀티 진입을 확인하고 공식 기록과 개인 설정이 보존되는지 검증합니다.

플러그인 로더, 권한 설정, 실행 예산, SDK 파일이나 안전 모드 명령은 이 문서에서 구현되었다고 간주하지 않습니다. 시험판에서 실제로 제공하는 인터페이스와 함께 문서화합니다.

## 1.9.0 안정화 정책 — 미래 적용

1.8.8 분석을 완성하고 제한된 플러그인 시험판을 검증한 뒤 1.9.0에서 본체 기능 범위와 호환성을 안정화합니다. 안정화 이후에는 본체 기능 확장을 계속 늘리기보다 버그·보안·호환성 수정과 플러그인 계열 확장에 집중합니다. 아래 초기 로드맵의 미완료 기능을 전부 구현해야 안정판이 된다는 뜻은 아닙니다.

`1.9.0`이라는 숫자나 배포 파일을 덮어 쓰며 영구 유지하지 않습니다. 본체 수정판과 플러그인은 각자 새 버전을 가지며, 공개 API는 호환성을 나타내는 버전을 별도로 관리합니다. 호환성을 깨는 변경은 기존 API를 조용히 바꾸지 않고 새 계약으로 구분합니다. 이 원칙은 명시적인 공개 API와 호환성에 따라 버전을 구분하는 [Semantic Versioning](https://semver.org/)을 참고합니다.

현재 고정 기준 `1.8.7`에서 미래의 안정판으로 이동하려면 별도 승인, 관련 문서·번역 동기화, 기존 모드와 기록의 호환성 검증이 필요합니다. 이번 계획 문서화는 기준선 변경이나 공개 릴리스·배포 실행을 뜻하지 않습니다.
